# Adversarial Review: Node Management Feature

## Summary

| Category           | Verdict            |
| ------------------ | ------------------ |
| Authentication     | ✅ Pass            |
| SQL Injection      | ✅ Pass            |
| Input Validation   | ⚠️ Warning (minor) |
| XSS                | ✅ Pass            |
| Migration Safety   | ✅ Pass            |
| Error Handling     | ✅ Pass            |
| Input Sanitization | ⚠️ Warning (minor) |

## Findings

### ⚠️ [Low] `credentials` and `extra` objects lack schema validation

- **Location**: `src/features/nodes/api/operations.ts:21-26`
- **Description**: The `readForm()` function accepts `credentials` and `extra` as `Record<string, unknown>` without any schema or content validation. While this is intentional (the content is protocol-specific), an attacker could inject arbitrary nested JSON objects that get persisted as-is. In practice this is low severity because auth is enforced and the data is only used within the controlled admin UI.
- **Fix**: Not required for current scope. If schema validation is desired, add per-protocol validation in `validateNodeForm()`.

### ⚠️ [Low] `JSON.parse` in `readForm()` could throw on malformed input

- **Location**: `src/features/nodes/api/operations.ts:21-26`
- **Description**: The `extra` and `credentials` fields are typed as `Record<string, unknown>` and stored as JSON strings. If the client sends a non-object value (e.g., a string or array), `JSON.stringify` in `nodeFromForm()` will still serialize it safely. However, the client-side `formFromNode()` in `node-manager.tsx:38-45` uses `JSON.parse` wrapped in try-catch, which handles failures gracefully.
- **Fix**: Already handled — try-catch in `formFromNode()` and `JSON.stringify` in `nodeFromForm()` ensure safe serialization.

### ✅ Authentication

- All 5 server functions (`listNodes`, `getNode`, `createNode`, `updateNode`, `removeNode`) use `.middleware([adminFunctionMiddleware])` which calls `authorizeAdminRequest()` on every request before the handler runs.
- The middleware validates the `Authorization: Bearer` header using SHA-256 + `crypto.subtle.timingSafeEqual()`.
- Auth runs before business logic — no bypass possible.

### ✅ SQL Injection

- All D1 queries use parameterized `?` bindings via `.bind(...)`.
- The dynamic `IN (?,?,?)` in `deleteMany()` uses generated placeholders but still binds values properly — no string interpolation.
- No concatenation of user input into SQL strings.

### ✅ XSS

- React's JSX automatically escapes all string values rendered in the template.
- User-supplied values (node name, server, port, country) are rendered as text content, not HTML.
- The `confirm()` dialog in the delete handler uses `node.name` as a plain string argument — no HTML injection possible.

### ✅ Migration Safety

- `0006_nodes.sql` is additive-only: creates a new `nodes` table with indexes, no ALTER, DROP, or RENAME operations on existing tables.
- Existing pool-based subscriptions continue to work alongside the new table.
- STRICT mode ensures data type integrity.
- CHECK constraints on name, server, and port prevent invalid data at the DB level.

### ✅ Error Handling

- Structured `AdminFailure` errors with typed codes (`invalid_request`, `not_found`, etc.).
- `adminFunctionMiddleware` catches all errors, logs internal ones to `console.error`, and returns generic messages to the user — no stack trace or DB internals leaked.
- `ValidationError` is caught and converted to `AdminFailure` with a user-facing Chinese message.

### ✅ Input Sanitization

- `readForm()` trims all string fields, validates port as a finite integer, and sets safe defaults.
- `validateNodeForm()` checks name (non-empty, max 200 chars), type (non-empty), server (non-empty, max 500 chars), and port (1-65535).
- `nodeFromForm()` further trims and sanitizes before persistence.

## Conclusion

**Non-blocking.** The node management feature is safe to deploy. No security vulnerabilities were found. The two ⚠️ warnings are minor and relate to the intentional lack of schema validation for protocol-specific credential fields, which is an acceptable design choice given the single-user auth model and controlled admin UI.

### Recommendations (optional, not blocking)

- If multi-user access is ever added, add per-protocol schema validation for `credentials` and `extra` fields.
- Consider adding a rate limit on CRUD operations if the app is exposed to public traffic.
